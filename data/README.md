# Data (M2)

All data in Wnesny is **synthetic (simulated)**. No real person, phone number, e-mail address or trip is used, and the
numbers say nothing about real Egyptian passengers. This follows the M1 proposal ("Simulated; no real people").

| Item | Value |
|------|-------|
| Source | Generated by this repository: `python -m simulation.generate` (seed 42 by default) |
| Size | 5 CSV files: 600 users, 32 interests, 50 areas, 2,967 user-interest pairs, 3,000 trips |
| Licence | Synthetic, no real people. Area names and approximate coordinates are typed in by hand (see "Known simplifications") |
| Period | 1 Aug 2026 to 31 Oct 2026 (92 days), simulated Cairo clock time |
| Where | `data/raw/` (not committed, because it is fully reproducible from the seed) |

## How to regenerate, check and load

```bash
python -m simulation.generate     # writes data/raw/*.csv        (same seed -> same files)
python -m simulation.validate     # integrity checks, exit code 1 if anything is wrong
flask --app run.py db upgrade     # create the schema (once)
python seed_interests.py          # interest catalogue (once)
python -m simulation.load         # validates, then loads users, rides, requests and reviews
```

The loader refuses to run twice and changes nothing if the data is invalid. Options for another size:
`python -m simulation.generate --seed 7 --users 800 --trips 4000`.

## Data dictionary

Types: **ID** = identifier, **category** = one value from a fixed list, **number** = measured or counted value.

### `users.csv` (one row per simulated user)

| Column | Meaning | Type | Note |
|--------|---------|------|------|
| `user_id` | Simulated user number | ID | 1 to 600. In the database a user gets a fake name (`Sim User 0001`) and an `example.com` e-mail. |
| `role` | What the user does on the platform | category | `driver`, `rider` or `both`. The database has one account type; this column only tells the simulator which trips a user can have. |
| `age_group` | Age band | category | `18-24`, `25-34`, `35-44`, `45+`. Bands only, no exact age. Not stored in the database yet. |
| `home_area_id` | The area where the user lives | ID | Foreign key to `areas.area_id`. |
| `gender_preference` | Whether the user wants a same-gender trip | category | `no_preference` or `same_gender`. Recorded only: the proposal lists it as a hard constraint, but the schema does not model gender yet. |
| `seats` | Seats the user offers as a driver | number | 1 to 3. Database V1.0 supports exactly one accepted passenger per ride, so only 1 is used there. |
| `avg_rating` | Mean rating received as a driver | number | 1 to 5, **empty** for users who never drove. Calculated from `trips.csv`. |

### `interests.csv` (interest catalogue, same 32 entries as `seed_interests.py`)

| Column | Meaning | Type | Note |
|--------|---------|------|------|
| `interest_id` | Interest number | ID | 1 to 32 |
| `name` | Interest name | category | Unique, e.g. `Photography` |
| `category` | Group of interests | category | 8 groups, e.g. `Technology`, `Sports`, `Music` |

### `user_interests.csv` (many-to-many link, one row per pair)

| Column | Meaning | Type | Note |
|--------|---------|------|------|
| `user_id` | The user | ID | Foreign key to `users` |
| `interest_id` | The interest the user has | ID | Foreign key to `interests`. No duplicate pairs. |

The proposal lists the interests as one "interest list" column. They are stored as a separate table here (third normal form),
which also matches the `user_interests` table in the database.

### `areas.csv` (about 50 coarse Cairo areas)

| Column | Meaning | Type | Note |
|--------|---------|------|------|
| `area_id` | Area number | ID | 1 to 50 |
| `name` | Area name | category | Unique, e.g. `Maadi` |
| `zone` | Part of Greater Cairo | category | Central Cairo, Giza, South Cairo, East Cairo, New Cairo, West Cairo |
| `latitude`, `longitude` | Approximate centre of the area | number | Degrees. **Typed in by hand, accurate to about 1 km, not taken from OpenStreetMap.** |
| `popularity` | Relative chance of being a trip destination or a home area | number | 1 (quiet) to 5 (busy). A simulation setting, not a measurement. |

### `trips.csv` (one row per completed trip: one driver, one rider)

| Column | Meaning | Type | Note |
|--------|---------|------|------|
| `trip_id` | Trip number | ID | 1 to 3,000, in order of departure time |
| `driver_id` | The driver | ID | Foreign key to `users`; the user's role is `driver` or `both` |
| `rider_id` | The passenger | ID | Foreign key to `users`; role `rider` or `both`; never the same person as the driver |
| `origin_area_id` | Where the driver starts | ID | Foreign key to `areas`. In 70% of trips it is the driver's home area. |
| `destination_area_id` | Where the trip ends | ID | Foreign key to `areas`; always different from the origin |
| `departure_at` | Departure date and time | date-time | `YYYY-MM-DD HH:MM`, simulated Cairo clock time, no time-zone conversion |
| `distance_km` | Road distance | number | Straight-line distance times 1.3. Minimum 3 km. |
| `duration_min` | Trip duration in minutes | number | Distance divided by a speed (22 km/h in peak hours, 38 km/h otherwise) times log-normal noise |
| `detour_min` | Extra minutes the driver needs to pick the rider up | number | Gamma distribution (mean about 7 min), capped at 25. Not calculated from the rider's home area. |
| `shared_interests` | Number of interests the driver and rider have in common | number | Counted from `user_interests.csv`, so it always matches the real overlap |
| `is_peak` | Peak-hour trip | category | `1` if the trip leaves between 07:00 and 10:00 or between 16:00 and 20:00, otherwise `0` |
| `rating` | Trip-compatibility rating given by the rider | number | Whole number 1 to 5, from the hidden rating model (below) |

## Simulation model

* **Users:** roles 35% driver, 55% rider, 10% both. The number of interests is Poisson (mean 5) limited to 1 to 10. Each
  user belongs to one of four interest clusters and draws 80% of their interests from it, so pairs of users overlap by
  different amounts.
* **Departure time:** a mixture of peak hours (60% of trips) and off-peak hours, on a random day of the period.
* **Rating:** one rating per trip from `simulation/rating_model.py`: a base score, plus a bonus for each shared interest
  (up to 4), minus a penalty for the detour and for peak hours, plus a fixed effect per driver and random noise, rounded
  to 1 to 5. The matching algorithm **must not** use this model (a test checks that `app/` never imports it), so
  that the evaluation is not circular. The coefficients are assumptions, not estimates from real data.

## Checks ("cleaning")

`python -m simulation.validate` checks, and reports with file and line number: expected columns; unique IDs and names;
valid foreign keys; roles allowed to drive or ride; driver is not the rider; origin is not the destination; ratings from
1 to 5; no negative detour or non-positive distance or duration; coordinates inside Greater Cairo; departure inside the
simulated period; `shared_interests` equal to the real overlap; no duplicate trips. It never edits or deletes rows.
The first findings (no missing values, no duplicates, `avg_rating` empty only for users who never drove) are in
[`notebooks/01_eda.ipynb`](../notebooks/01_eda.ipynb).

## What the loader stores in the database

`simulation.load` creates users, their interests, and for every trip one completed `rides` row, one accepted
`ride_requests` row and one `reviews` row (rider rates driver). `areas.csv` has no table: the ride stores the area name as
its address plus the area coordinates. Chat messages, conversations and notifications are not simulated.

## Known simplifications

* Area coordinates are approximate and typed in by hand. Check them against OpenStreetMap (ODbL) and cite it before M5.
* The detour is random, not calculated from the rider's home.
* One rating per trip (rider about driver); there is no review from the driver.
* Pickup of the rider is not a separate area: each trip has one origin and one destination.
* The proposal's `trips` and `ratings`, `matches` and `drivers` and `riders` tables differ from the implemented schema.
  See `docs/proposal/README.md` for the list of differences.
